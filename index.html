02 / Method

5つの階層を、
順番に降りていく。

「レビュー」の実力は、どこで止まるかで決まります。私たちは上から順に降りていき、各層で得られたものだけを材料にします。

01 / 05

公表資料

Primary notice

社告・再発防止策・監督官庁の資料。何が「公表された事実」で、何が報道ベースかを最初に切り分けます。

ここが曖昧な指摘は、経営層への説明で必ず崩れます。

02 / 05

仕様書・BCP

RFC / BCP

RFC と Security Best Current Practice を原文で読み、MUST の範囲と、仕様が沈黙している箇所を分けます。

「推奨」を「必須」として渡さないことが、実装チームの信頼につながります。

03 / 05

設定

Configuration

ライブラリの既定値、プロキシ、CORS、Cookie、トークン有効期間。仕様が及ばない判断は設定に宿ります。

同じコードでも、設定だけで防御が反転する箇所を特定します。

04 / 05

コード

Implementation

検証の分岐が本当に効いているか。ミドルウェアの順序と、例外経路でのバイパスまで確認します。

「入っている」ことと「効いている」ことは、別の話です。

05 / 05

実行結果

Observed behaviour

拒否されるはずの要求を、実際に送って確かめます。期待した応答とログの残りが証拠になります。

許可された環境で、合意した期間だけ。ここを超えないことが前提です。

03 / Depth

仕様の一行を、
検証できる問いに変える。

レビューの一場面を、そのまま4つ置いています。原文の要求・どこを見るか・何を送るか・何が起きるべきか。この順で読める形で渡します。

OAuth 2.0認可コードは、認可を始めた要求と結び付いていますか。

If a client sends a valid PKCE code_challenge parameter in the authorization request, the authorization server MUST enforce the correct usage of code_verifier at the token endpoint.

認可要求で有効な code_challenge を受け取った場合、認可サーバはトークンエンドポイントで code_verifier の正しい利用を強制しなければならない。

RFC 9700 §2.1.1 — Authorization Code Grant Clients

どこを見る

認可要求で code_challenge を記録し、トークン交換時に照合している箇所。S256 以外の challenge_method を受け付けていないかも同時に確認します。

何を送る

正しい認可コードに対して、対応しない code_verifier を送る。

何が起きるべきか

トークンを発行せず拒否する。ログには利用可能な範囲で拒否理由が残る。

「PKCE を有効にした」だけでは結論になりません。検証が効いているかを、下向き攻撃（challenge なしの要求で verifier だけ送る）のケースまで含めて確かめます。この1件を、最後まで掘った解説を読む

OAuth 2.0リダイレクトURIは、事前登録値と完全一致で比較されていますか。

When comparing client redirection URIs against pre-registered URIs, authorization servers MUST utilize exact string matching except for port numbers in localhost redirection URIs of native apps.

クライアントのリダイレクトURIを事前登録済みのURIと比較するとき、ネイティブアプリの localhost リダイレクトURIのポート番号を除き、認可サーバは完全一致による照合を用いなければならない。

RFC 9700 §2.1 — Protecting Redirect-Based Flows

どこを見る

部分一致・プレフィックス一致・ワイルドカードを許している登録運用。開かれたリダイレクタがクライアント側に残っていないかも見ます。

何を送る

登録済みのパスの前置部分に一致する、別の経路やサブドメインへ向かうURIを認可要求に使う。

何が起きるべきか

認可画面を進めず、redirect_uri は無効として拒否する。

「自社ドメインなら許す」という運用は、ここで壊れます。仕様は例外を1つしか挙げていない、という話を根拠にできます。

JWT署名が正しい別用途のトークンを、受け入れていませんか。

the relying party or application MUST validate the audience value, and if the audience value is not present or not associated with the recipient, it MUST reject the JWT.

信頼する側（リライングパーティ）またはアプリケーションは aud の値を検証しなければならず、aud が存在しない場合や受け手と関連付けられない場合は、その JWT を拒否しなければならない。

RFC 8725 §3.9 — Use and Validate Audience

どこを見る

署名検証と iss チェックの後に、aud をこの API の値と照合しているか。内部API間でトークンが流れ込んでいないかをあわせて確認します。

何を送る

署名も issuer も正しいが、別のサービス向けに発行されたトークンを送る。

何が起きるべきか

認証情報として受け入れず、保護対象へのアクセスを拒否する。

「署名が通った」は検証の途中経過でしかありません。用途の境界まで確かめて初めて合格と呼べます。

HTTPタイムアウト後の再送で、注文は二重になりませんか。

Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent.

この仕様が定義する要求メソッドのうち、冪等なのは PUT、DELETE、および安全な要求メソッドである。

RFC 9110 §9.2.2 — Idempotent Methods

どこを見る

POST の再送が起きたときに業務処理を一度に束縛する識別子と、その一意性・有効期間・同時実行の扱い。

何を送る

応答を読む前に同じ業務要求を再送する。同時に2本流すケースも入れる。

何が起きるべきか

合意した業務仕様に従い、同じ注文を二重に作成しない。

注意すべきは逆方向です。HTTP は冪等の作り方を規定しないので、キー方式の選択は事業設計の話になります。ここを仕様側のせいにして放置している実装をよく見ます。

04 / Patterns

壊れる場所は、
いつも同じです。

仕様が名指ししている壊れ方を4つ並べました。要求の原文・どこを読むか・何を試すか・そうなっていれば直っている、の同じ順で書いています。顧客事例ではなく、RFC が挙げている壊れ方の棚卸しです。

  1. P-01

    state が「画面の引き継ぎ」になっていて、CSRF の鍵になっていない

    state にステップ番号や戻り先を入れておき、コールバックでは「認可が終わった」という理由だけで中身を検証せずに受け入れます。認可エラーに飛んだ経路では、state を読むコード自体が走っていません。

    • 設定
    • コード
    Otherwise, one-time use CSRF tokens carried in the state parameter that are securely bound to the user agent MUST be used for CSRF protection

    PKCE も nonce も使えないなら、使い捨ての CSRF トークンを state に載せ、しかもそれをユーザーエージェントへ安全に紐付けた形で使わなければならない。

    RFC 9700 §2.1確認日 2026-10-31
    どこを読むか
    認可要求を作った側（サーバ）が state を保存しているか。コールバックで比較したあと削除しているか。エラー分岐でも比較しているか。
    何を試すか
    別のブラウザセッションで同じコールバックを再生する。一度使い終えた state をもう一度送る。
    直った状態
    どちらも認可を続けず、開始からやり直させる。ログには拒否が残り、トークンは発行されない。

  2. P-02

    PKCE を「有効にした」のに、challenge を消されると外れる

    challenge が付いた要求の検証だけを作ると、攻撃者は challenge を外した認可要求を作るだけで良くなります。設定画面の PKCE 項目はオンのまま、実質は効いていません。

    • 設定
    • 実行結果
    Beyond this, to prevent PKCE downgrade attacks, the authorization server MUST ensure that if there was no code_challenge in the authorization request, a request to the token endpoint containing a code_verifier is rejected.

    認可要求に code_challenge が無かったなら、トークンエンドポイントに code_verifier を伴う要求は拒否しなければならない。ダウングレード対策はこの形での必須として書かれています。

    RFC 9700 §4.8.2確認日 2026-10-31
    どこを読むか
    challenge の有無を認可コードに紐付けて保持しているか。その判定がトークン交換側の分岐に入っているか。
    何を試すか
    challenge なしの認可要求で発行したコードに、もっともらしい verifier を添えて交換する。
    直った状態
    その交換は拒否される。client 単位（または全体）で PKCE が必須になり、外した要求がそもそも通らない。

  3. P-03

    リフレッシュトークンが、更新されない鍵として残り続けている

    SPA やネイティブアプリ（client secret を持てない側）で、更新しても古いリフレッシュトークンが生きたまま。端末かブラウザを盗まれた時点で、有効期限の切れない鍵になります。

    • 設定
    • コード
    Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation as described in Section 4.14.

    public client のリフレッシュトークンは、送手に縛るか、ローテーションのどちらかにしなければならない。二択です。

    RFC 9700 §2.2.2確認日 2026-10-31
    どこを読むか
    リフレッシュ応答で返した新しい値だけを受理しているか。旧値の受理を取り消す処理があるか。保存先（ブラウザ側ストレージ）はどこか。
    何を試すか
    リフレッシュの前後で得た2本のトークンを、それぞれ使ってアクセストークンを取りに行く。
    直った状態
    古いほうは拒否され、検知した場合はその系統のトークンがまとめて失効する。少なくとも恒久の鍵は残らない。

  4. P-04

    認可の直後のページが、外部のリソースを読みに行っている

    コールバック後に解析タグ・CDN・ favicon を読むと、その要求の Referer に認可コードを載せた URL が乗ります。Referrer-Policy を置いていない応答は、ここで素で漏れます。

    • 公表資料
    • 設定
    The page rendered as a result of the OAuth authorization response and the authorization endpoint SHOULD NOT include third-party resources or links to external sites.

    認可の応答の結果として描画されるページと認可エンドポイントは、第三者のリソースや外部サイトへのリンクを含めるべきではない。

    RFC 9700 §4.2.4確認日 2026-10-31
    どこを読むか
    認可応答の応答ヘッダー。そのページが読む外部ドメイン。コードをクエリで受けたあとの画面遷移（書き換え前に残る URL）。
    何を試すか
    認可応答の Referrer-Policy を読み、そのページが発火させる外部要求を実際に数える（許可された環境で）。
    直った状態
    no-referrer か same-origin が効いていて、認可の直後の応答に外部読み込みが残らない。

引用は RFC 9700（OAuth 2.0 Security Best Current Practice）からの逐語で、節番号にリンクしています（確認日 2026-10-31）。試す手順は、対象・期間・やめる条件を合意できた環境でだけ実施します。

07 / AI

AIは、速い。
だから証拠にはならない。

読解と下書きに使い、結論には人の名前を残します。顧客の情報をどこに入れるかは、契約の前に決めるべき項目だと考えています。

使う工程

  • 一次資料とRFCの横断的な検索と突合
  • 読了に時間のかかるコードの下読み
  • 負のケース（拒否条件）のテスト案起草
  • 報告書の骨子と用語の統一

やらないこと

  • 結論・重大度の判断・納品物の責任は人が持つ
  • 顧客の生データ・認証情報・ソースを無断で投入しない
  • 生成結果をそのまま指摘として書かない
  • 道具と制約（モデル・アクセス区分）は報告書に記録する

検証済みのモデルアクセスについて

Anthropic の Cyber Verification Program、OpenAI の Trusted Access for Cyber は、防御的なセキュリティ作業向けの検証済みアクセスです。顧客への提供には別途承認が必要とされていることを踏まえ、自社の事業形（自社スタッフが顧客のシステムに対して働き、完成した成果物だけを渡す形）で申請できる経路を確認しています。

ANTHROPICCyber Verification Program（公式）OPENAITrusted Access for Cyber（公式）STATUS申請方針の整理中。承認・契約関係は主張しません。

11 / FAQ

よくある、
最初の問い。

許可のない環境の検査も可能ですか？

できません。対象・期間・手法・やめる条件を書面で合意できた環境だけを扱います。外部公開された資産の能動的なスキャンも、所有者の許可がない限り行いません。

費用と期間はどのくらいですか？

範囲によって変わるため、一律の価格表は置いていません。初回はお互いの認識合わせにとどめ、お見積りを書面で提示してから着手します。

機密情報やログを渡すのが心配です。

最小化が原則です。マスキング済みの設定値や再現手順で足りる場合が多く、生ログの共有は必要な範囲と期間を合意した場合だけにおさめます。秘密保持契約にも個別に対応します。

AIツールに社内情報を入れて調べさせますか？

入れません。生成AIは読解と検証手順の起草に使い、顧客データを投入しない運用を原則にしています。使う道具と、そのときの制約は報告書に書き残します。

レポートは経営層と開発チーム、どちら向けですか？

両方です。リスクの言葉で意思決定できる要約と、コード・設定・テスト名まで落ちた実施手順を、同じ報告書の中に分けて書きます。
